# Implementation Plan: Additional CV File Formats (DOCX & Images)

**Branch**: `010-cv-file-formats` | **Date**: 2026-06-07 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/010-cv-file-formats/spec.md`

---

## Summary

Extend the existing CV ingestion path to accept DOCX (`.docx`) and image (`.jpg`/`.png`)
files in addition to PDF. DOCX is parsed with `python-docx` (paragraphs + tables) and
reuses the existing quality heuristic to fall back to Azure Document Intelligence when
the extracted text is too sparse; images route straight to Document Intelligence. The
public application endpoint widens its accepted MIME types (keeping the 10 MB cap) and
the application form advertises the new formats. Everything downstream — chunking,
embedding, hybrid search, screening, storage — is unchanged, so DOCX/image CVs produce
identical screening output to PDFs.

---

## Technical Context

**Language/Version**: Python 3.12 (backend), Node 20 / TypeScript 5 (frontend)

**Primary Dependencies**: existing `OcrService` (PyMuPDF + `azure-ai-formrecognizer`),
FastAPI, SQLAlchemy async; **adds `python-docx`** to the backend for DOCX extraction.

**Storage**: No schema change. Existing `applications.cv_extraction_method` records the
path used (`pymupdf` | `document_intelligence`); DOCX adds `docx` as a recorded source.

**Testing**: `pytest` + `pytest-asyncio`; CV screening is a Constitution-VIII TDD
domain, so DOCX and image extraction get failing-first tests before implementation.

**Target Platform**: Docker Compose (dev) / Azure Container Apps (prod) — unchanged.

**Project Type**: Multi-service web app (backend + agents + frontend) — unchanged.

**Performance Goals**: DOCX/image screening within the same ≤ 2 min SLA as PDF (SC-001).

**Constraints**: 10 MB upload cap across all formats; English-language CVs; `.docx`
only (no legacy `.doc`); single-image CVs only.

**Scale/Scope**: Small, additive feature — 8 tasks (T001–T008), no new endpoints or
entities, one new backend dependency.
